我先把小红书、X、知乎等信息源封装成命令行工具，让 Codex 做任务时能自己跨平台搜索、阅读资料，省去我手动查询和搬运内容的操作。

在此基础上，又做了给自己日常阅读用的“拾流”：聚合多个平台想看的内容，结合兴趣推荐和 DeepSeek 的搜索辅助、分析总结，减少无效浏览，更方便地获取有价值的信息。

## 1. 整体架构

项目分为两层：`info-collector` 提供各平台的搜索、读取命令；`info-hub` 复用这些命令，负责内容存储、阅读、推荐与 AI 任务。采集层既可以由 Codex 按需调用，也可以交给拾流后台定期调用。

## 2. 多平台信息采集

### 2.1 信息源与开源项目选型

采集能力主要基于现成开源项目，再补充适合自己使用的命令入口、输出格式和兼容修复。下面列的是本项目实际使用的方案，以及已经接入的主要能力；不代表上游项目的所有功能都已经接进拾流。

| 信息源       | 使用的项目或接口                                                                                                             | 本项目的接入方式与能力                                                                  |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 小红书       | [xiaohongshu-cli](https://github.com/jackwener/xiaohongshu-cli)                                                              | 封装搜索、帖子详情、评论和信息流读取，保留媒体链接                                      |
| X / Twitter  | [twitter-cli](https://github.com/public-clis/twitter-cli)                                                                    | 封装搜索、帖子详情、用户近帖和时间线；本地补丁修复搜索请求初始化                        |
| Instagram    | [instagrapi](https://github.com/subzeroid/instagrapi)、[Instaloader](https://github.com/instaloader/instaloader)             | 前者用于关键词搜索，后者读取帖子正文、媒体链接和账号近帖                                |
| 知乎         | [zhihu-cli](https://github.com/Xiaofan629/zhihu-cli)，安装包名为 `zhihu-tui`                                                 | 复用回答读取能力，搜索由本地脚本补充网页请求；已验证搜索和回答正文                      |
| B 站         | [bilibili-cli](https://github.com/public-clis/bilibili-cli)、[bilibili-api-python](https://github.com/Nemo2011/bilibili-api) | 获取搜索结果、视频详情、评论和可访问字幕；补充详情接口兼容处理                          |
| Hugging Face | 官方 [huggingface_hub](https://github.com/huggingface/huggingface_hub) SDK                                                   | 模型搜索、热榜、模型卡、论文列表与详情；模型榜单尚未纳入拾流自动轮询                    |
| arXiv        | 官方 [arXiv API](https://info.arxiv.org/help/api/index.html)                                                                 | 直接请求 Atom API，获取论文元数据、摘要和 PDF 链接，不解析论文全文                      |
| RSS / Atom   | [feedparser](https://github.com/kurtmckee/feedparser)                                                                        | 解析订阅，增量拉取和去重；Feed 只有摘要时，拾流再按需读取原网页                         |
| 微信公众号   | [wechat-download-api](https://github.com/tmwgsicp/wechat-download-api)                                                       | 复用 HTTP 与正文解析模块，按文章链接读取正文、图片并保存 Markdown；没有部署完整上游服务 |

采集器还接入了 [NapCatQQ](https://github.com/NapNeko/NapCatQQ) 和 [wechat-ai-memory](https://github.com/ikevss/wechat-ai-memory)，用于按需导出 QQ 群消息和本机微信记录。这两类私密内容不混入公开推荐，也不交给拾流的模型处理。

这些项目不是装好就能永久使用：部分来源依赖登录状态，接口也可能变化。例如 Instagram 的搜索和详情分别使用了两个库；X、B 站则保留了可重复应用的兼容补丁。每个来源固定依赖版本、使用独立环境，避免一次升级影响其他入口。

### 2.2 将采集能力封装成 CLI

各来源最终都提供一个 Python 脚本入口。以当前采集器为例，在配置好依赖和所需登录状态后，可以运行：

```powershell
# 安装指定来源的独立环境
python setup_sources.py xhs twitter huggingface

# 搜索帖子或模型
python xhs.py search "AI 修图"
python twitter.py search "AI photo editing" --max 3
python huggingface.py models --sort trending --max 3
```

这些是本项目的封装命令，上游原生命令分别见对应仓库。封装主要统一四件事：命令参数、运行环境、结果文件和失败状态。

大部分公开来源的结果采用下面的外层结构，`data` 内仍保留各平台实际返回的字段：

```json
{
  "schema_version": 1,
  "source": "twitter",
  "operation": "search",
  "query": {},
  "fetched_at": "2026-10-20T12:00:00+08:00",
  "data": {}
}
```

这是格式示意，时间和数据不是实际采集结果。脚本将正文写入结果文件，标准输出返回成功状态和文件路径；失败返回 JSON 错误与非零退出码。调用方不用从终端里一大段自然语言日志猜测有没有成功，也能保留原始结果供后续重读。

### 2.3 让 Codex 按需组合调用

有了命令入口，临时调查可以直接这样提需求：

> 帮我找几个 AI 修图项目。先去小红书和 X 看实际玩法，再查相关代码和说明，比较能做什么、部署条件和限制，保留来源链接。

Codex 可以先选择来源和关键词，读取搜索结果，再补查帖子详情、评论或模型卡。如果材料不足，就换关键词或增加来源，最后基于取得的内容整理。它的本地执行能力见 [OpenAI 官方 CLI 文档](https://learn.chatgpt.com/docs/codex/cli)，各平台的实际访问能力则来自前面的采集器。

灵活性在于，调查顺序可以随问题变化。今天找修图工具，明天查账单导出方法，复用同一组命令即可，不必给每类需求预先开发一套 Bot 指令和固定处理流程。个人使用时，先把工具做成 CLI，配上用法和限制说明，就已经能交给助手组合调用。

Bot 或 MCP 也可以复用这些工具，只是目前没有为这层接口单独搭服务。CLI 同样需要维护登录和接口；遇到失败时，当前聊天里的 Codex 可以借助已经提供的浏览器工具继续查，采集脚本本身不会自动操控浏览器。

## 3. 信息聚合与阅读管理

CLI 解决了按需查资料的问题。要做每天浏览的信息流，还需要长期保存内容、组织更新，并记住自己看过和收藏过什么。拾流用 FastAPI 提供后端，SQLite 保存帖子、任务和反馈，React 提供阅读界面。

### 3.1 内容入库、去重与正文补全

后端按来源启动对应采集脚本，读取结果文件，再转换成包含标题、作者、原始链接、发布时间、正文和媒体信息的帖子记录。采集器继续独立维护，网页不复制一套平台接入逻辑。

入库和补全时，主要处理三件事：

- **按来源和帖子 ID 去重。** 同一条帖子被多次搜到，合并到已有记录；不同平台转发的相似内容，目前没有做完整的语义去重。
- **区分搜索摘要与原文。** 已经取得的长正文不会被后续短摘要覆盖；首次打开详情时，再按需补全缺失正文。
- **分开保存原文与模型结果。** 摘要和译文不覆盖原文，源内容变化后使对应缓存失效；刷新失败仍保留已取得的内容。

图片按实际采集链接读取并缓存。小红书、Instagram 的图片签名可能过期，加载失败时重新获取原帖中的链接，再按图片标识匹配，避免更新后显示错图。

### 3.2 增量采集与统一阅读

主动搜索会先展示已有结果，再补充新采集；后台则按兴趣定期收集候选。采集、模型处理与网页请求分队列，避免一篇长文的翻译阻塞普通浏览。

阅读界面保留原帖图文、来源和原文链接，支持收藏、不感兴趣和来源屏蔽。已展示或已读记录参与后续轮换；正在阅读时，新内容补全和图片加载尽量保持当前位置，后台更新不直接把列表重排。

这一层不依赖模型一直在线。关闭 AI 后，已有内容仍然能浏览、收藏和按原词搜索。

## 4. AI 辅助推荐、搜索与内容分析

拾流目前直接调用 DeepSeek API，模型配置为 `deepseek-flash`。常驻任务有固定输入和输出，不需要每次启动 Codex，也不向模型提供命令执行或浏览器工具。需要结构化结果时使用 [DeepSeek JSON Output](https://api-docs.deepseek.com/zh-cn/guides/json_mode/)，后端继续校验字段、类型和帖子 ID，再保存结果。

### 4.1 兴趣解析与反馈推荐

用户先描述想看和不想看的内容，模型整理出兴趣主题、搜索词和排除项；对已取得的帖子文本，模型再提取主题标签。推荐使用这些标签与阅读反馈计算排序。

具体流程是：

```text
兴趣描述 → 主题与搜索词 → 采集候选帖子 → 提取主题标签
                                              ↓
网页推荐 ← 规则排序与探索混排 ← 点赞、收藏、浏览等反馈
```

当前规则综合主题匹配、内容新鲜度、作者偏好和已读状态；不感兴趣会降低对应内容的推荐权重，排序后再减少同来源、同作者连续出现。这是可以修改的规则与反馈方案，没有训练独立推荐模型。

探索比例默认约为 20%，其余优先选择贴合兴趣的内容，可以在界面调整。探索候选优先考虑相关但较陌生的主题；不足时补位，因此比例是组织目标，不保证每批都严格满足。

### 4.2 跨来源、跨语言搜索

跨平台搜索除了同时调用多个入口，还需要处理关键词的语言差异。例如查一个日本摄影师，中文名、日文名和英文写法，可能分别找到不同内容。

现在先立即搜索原词，再由模型生成等义的英文关键词，以及有把握的原语言名称：中文来源保留原词，X、Instagram 最多增加两个查询，arXiv 和 Hugging Face 补充英文查询。扩展词会显示出来，允许修改或关闭；链接、账号和精确查询表达式不翻译。

补搜结果归入原始查询，按来源和帖子 ID 去重，语言规划结果缓存复用。这样模型变慢或补搜失败，也不会让原词搜索一直等着。召回范围仍受各平台搜索能力限制。

### 4.3 图文摘要与按需翻译

帖子详情默认保留原文，用户需要时再生成摘要或译文。长正文分段处理；图文摘要将实际取得的文案和图片交给模型，按批次读取后合并结果，页面标注已读图片数量和失败项。只有摘要或文案时，也会明确说明处理范围。

英文文章翻译后可以切换原文和中文，译文独立缓存，保留段落、图片和链接位置。模型负责帮助快速理解，核对细节仍然回到原帖。视频目前只可能读取封面，不分析视频画面和音频。

## 5. 私人服务器部署与访问

拾流已经部署到家里的闲置 Windows 电脑上。采集器、网页后端、SQLite 数据库和图片缓存都在服务器运行，开发电脑关机后仍可使用。

部署时保留 `info-hub` 与 `info-collector` 相邻的目录关系：后端通过本机子进程调用采集器，构建好的前端由同一个后端服务提供。服务器无需另外运行前端开发服务，也不用给每个信息源单独开放网络接口。

我用 SSH 更新代码和查看运行状态，计划任务负责后台启动、异常恢复和每日数据库备份。手机加入同一个 Tailscale 私人网络后，通过 Serve 提供的 HTTPS 入口访问网页；DeepSeek Key 和采集凭据保留在服务器端。

具体的 Windows SSH、Tailscale 和私人 HTTPS 配置，放在之前的[《把闲置电脑变成私人服务器》](/posts/windows-private-server/)中，这里直接复用那套部署方式。
